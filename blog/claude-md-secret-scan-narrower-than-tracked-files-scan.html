CLAUDE.md gets read into every session — cc-doctor's check on it only catches 3 shapes of secret

By HiroCheck · Published 2026-08-22

Claude Code's own documentation describes CLAUDE.md as memory that gets merged automatically at the start of a session from up to three places: a global copy at ~/.claude/CLAUDE.md, the project root, and any subdirectory Claude reads a file from. Unlike a config file a linter might flag once and a developer might never open again, this file is written to be read — by a person doing onboarding, and by the model, on every single session that touches the project (or, for the global copy, every project on the machine).

That combination — a file people treat like documentation, but that a scanner-shaped mental model would treat like config — is exactly the category GitGuardian's 2026 State of Secrets Sprawl report flags as underestimated: about 28% of secret sprawl it tracked happened outside code repositories entirely, in collaboration and productivity tooling, and internal repositories were found 6x more likely than public ones to contain hardcoded secrets — the audience-of-one assumption behind a private project's CLAUDE.md is precisely the condition the report ties to lower scrutiny, not lower risk.

What cc-doctor's CLAUDE.md check actually looks for

The check is one regex against one file: /BEGIN PGP|PRIVATE KEY|AKIA[0-9A-Z]{16}/. That's three shapes — a PGP-armored block header, the string "PRIVATE KEY" (as in a PEM header), and an AWS access key ID — plus two unrelated checks in the same file: a missing-or-empty warning, and a size warning past 40,000 characters (a proxy for "burning context budget on every session", not a security finding). There's no GitHub PAT pattern (ghp_...), no Slack token, no Anthropic/OpenAI-style key (sk-...), and no generic api_key: "value" catch-all — the four things cc-doctor's separate secrets-scan check looks for everywhere else in the repository.

Why that narrowness mostly doesn't matter — for the tracked case

cc-doctor's secrets-scan check works by listing every file git currently tracks (git ls-files) and running its full five-pattern-plus-generic set against each one's content. A project-root CLAUDE.md that's committed to the repository is, from that check's point of view, just another tracked file — so a ghp_ token or a quoted api_key: "..." value sitting in it gets caught there, independently of what the narrower claude-md check does. In the common case — CLAUDE.md committed at the project root, under the scan's 1 MB file-size cap — the two checks overlap, and the AWS-key pattern in particular is redundant: it's the same regex in both files.

Where the gap is real

The secrets-scan check's file list comes from git ls-files, so its coverage stops exactly where git tracking stops. Two concrete cases fall outside both checks entirely:

  • A CLAUDE.md deliberately kept out of git — gitignored, or scanned before the first git add. It never appears in git ls-files, so secrets-scan never sees it; only the narrower three-pattern claude-md check would catch a credential there, and only if it happens to be one of those three shapes.
  • The global ~/.claude/CLAUDE.md — by Claude Code's own merge behavior, this file's contents get folded into every project's session on the machine, but it lives in the user's home directory, outside any repository. cc-doctor's checks all take a root argument and operate on that one target repo; neither check reads anywhere outside it. A repo-scoped scanner — this one or any other built the same way — structurally cannot see a file that isn't part of the repo being scanned.

Subdirectory CLAUDE.md files don't add a third case: if they're committed, they're just more entries in git ls-files, and secrets-scan's whole-tree pass already covers them the same way it covers the root file.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README.
