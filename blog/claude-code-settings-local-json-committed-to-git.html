settings.local.json is supposed to stay local — what happens when it gets committed

By HiroCheck · Published 2026-08-15

Claude Code splits its permission settings across two files by design: .claude/settings.json for team-shared, committed policy, and .claude/settings.local.json for one contributor's personal, machine-local overrides. When Claude Code itself writes to the local file, it adds the pattern to .gitignore automatically. The split only holds up, though, if that entry actually stays in place — a manually created settings.local.json, a .gitignore edited by hand later, or a file added before the ignore rule existed can all end up committed anyway.

What actually leaks

The file isn't just preferences. It's the same permissions.allow / permissions.deny structure as the team file, so whatever one contributor approved locally — a broad Bash(*) grant they meant to scope down later, a path specific to their own machine, an MCP server they were testing — becomes visible, and in effect proposed, to everyone who clones the repo. It's a narrower version of the same problem as committing a .env.local: individually-scoped config merging into shared history.

A second, unrelated failure mode: hooks that silently do nothing

Separately from the git-tracking question, both settings files can define hooks — commands Claude Code runs automatically on events like a tool call or session start. A hook entry is just a string command, and if it references a script by relative or absolute path (.sh, .js, .py, .mjs, .cjs), there's no built-in feedback if that path is wrong. A renamed file, a script that only exists on the original author's machine, or a typo in the path all produce the same result: the hook is configured, Claude Code doesn't complain, and it just never runs. The gap between "configured" and "working" is invisible without a check that actually resolves the path against disk.

What cc-doctor checks

cc-doctor is a free CLI that reads a repo's Claude Code config the same way Claude Code does. For these two patterns specifically, it: (1) checks whether .claude/settings.local.json exists on disk and is tracked by git (via git ls-files), and warns if so, independently of what the file contains; (2) for every hook command in both settings files that looks like a script path, resolves that path against the repo root and warns if nothing exists there. Neither check requires network access or an API key — both run against the local filesystem and git index.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README.
