cc-doctor flags Bash(*) in settings.json — not bare Bash, which Claude Code's own docs say grants the same unrestricted access

By HiroCheck · Published 2026-09-19

Claude Code's permission rules come in two shapes: a scoped rule like Bash(rm -rf *), which matches only commands fitting that pattern, and a bare tool name with no parentheses at all, like Bash, which — per Claude Code's own permissions documentation — matches every call to that tool with no scoping whatsoever. The docs don't just mention this as an edge case; they recommend it as the way to allow all Bash commands without prompting: "To run all Bash commands without prompts except for a few you want blocked, add "Bash" to your allow list and register a PreToolUse hook that rejects those specific commands." A bare allow entry is, functionally, the same unrestricted grant as Bash(*) — arguably a stronger one, since it also skips the scoped-pattern matching the parenthesized form goes through.

cc-doctor's settings-permissions check doesn't know about this second shape. It has two separate mechanisms for catching risky Bash grants, and both are written for the parenthesized form only.

Two checks, one blind spot

From lib/checks/settings-permissions.js: six fixed regular expressions (all covered in an earlier post on this blog) test each allow rule for known-dangerous parenthesized patterns — every one anchored to ^Bash\(, an opening parenthesis required. Separately, a dedicated check at line 74 looks for unrestricted access:

if (allow.includes('Bash(*)') && deny.length === 0) {
  report.error(
    'settings-permissions',
    `${relPath} grants unrestricted Bash access ("Bash(*)") with no deny rules.`,
    relPath
  );
}

This is the check the README describes as catching "unrestricted Bash(*) permission grants with no deny rules" — and it does, correctly, for that exact string. But it's an exact-string includes() match, not a check for "does this file grant unrestricted Bash access." A bare "Bash" entry means the same thing to Claude Code at runtime and means nothing to either of cc-doctor's two mechanisms: it doesn't start with Bash(, so none of the six regexes fire, and it isn't the literal string Bash(*), so the dedicated check doesn't fire either.

Verified directly, side by side

Two otherwise-identical .claude/settings.json files differing only in that one line, scanned by the unmodified CLI:

// unrestricted-1/.claude/settings.json
{ "permissions": { "allow": ["Bash(*)"] } }

// unrestricted-2/.claude/settings.json
{ "permissions": { "allow": ["Bash"] } }
$ cc-doctor unrestricted-1
[ERROR] settings-permissions: .claude/settings.json allows a high-risk
  command pattern: "Bash(*)"
[ERROR] settings-permissions: .claude/settings.json grants unrestricted
  Bash access ("Bash(*)") with no deny rules.
cc-doctor: 2 error(s), 0 warning(s), 1 info.
$ echo $?
1

$ cc-doctor unrestricted-2
cc-doctor: 0 error(s), 0 warning(s), 1 info.
$ echo $?
0

Both configurations grant Claude Code the same thing: every Bash command runs without a permission prompt. One exits 1 with two errors. The other exits 0, clean.

Why this isn't just a missing regex

The dangerous-pattern-list post on this blog is about an open set — new destructive command shapes that could always be added to the six patterns, with the list never quite catching up. This is a narrower, closed gap: there is exactly one other syntactic form Claude Code recognizes for "match every Bash call," it's documented, and it isn't represented in either of the two checks that exist specifically to catch unrestricted Bash access. Extending the existing Bash(*) check to also match a bare "Bash" string (or a bare-name entry for any tool, since the same convention applies beyond Bash) would close it without adding a single new regex.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's accuracy corpus, the tool's recall is 100% with a 0% false-positive rate — full methodology in the project README. That corpus targets the secrets-scan check; the settings-permissions gap described here doesn't change those numbers, since a bare-tool-name allow rule isn't part of the corpus.
