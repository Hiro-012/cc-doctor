A Stripe live key hardcoded in .mcp.json slips past every one of cc-doctor's secret checks

By HiroCheck · Published 2026-09-10

cc-doctor has two independent layers that can catch a hardcoded credential: mcp-config.js, which inspects .mcp.json specifically, and secrets-scan.js, which greps every git-tracked file as a general backstop. Tracing both against a Stripe secret key shows neither one fires — not because the key is disguised, but because both checks were built around a small, fixed list of formats that doesn't include it.

The specific check: four providers, hardcoded

function looksLikeHardcodedSecret(value) {
  ...
  return (
    /^sk-[a-zA-Z0-9]{16,}$/.test(value) ||       // OpenAI/Anthropic-style
    /^ghp_[a-zA-Z0-9]{20,}$/.test(value) ||      // GitHub PAT
    /^AKIA[0-9A-Z]{16}$/.test(value) ||          // AWS access key id
    /^xox[baprs]-[a-zA-Z0-9-]{10,}$/.test(value) // Slack token
  );
}

Running this against fake-but-correctly-shaped tokens for three providers that aren't on the list:

looksLikeHardcodedSecret("sk_live_51H8xJ2KZvczFKz...")  // Stripe secret key   → false
looksLikeHardcodedSecret("rk_live_51H8xJ2KZvczFKz...")  // Stripe restricted   → false
looksLikeHardcodedSecret("glpat-ABCDEFGHIJKLMNOPQRST")  // GitLab PAT          → false
looksLikeHardcodedSecret("npm_ABCDEFGHIJKLMNOPQRSTUVWX") // npm access token   → false

looksLikeHardcodedSecret("sk-ABCDEFGHIJKLMNOPQRSTUVWX")  // OpenAI/Anthropic   → true
looksLikeHardcodedSecret("ghp_ABCDEFGHIJKLMNOPQRSTUVWX") // GitHub             → true

Stripe's own documentation specifies sk_test_ / sk_live_ for secret keys and rk_test_ / rk_live_ for restricted keys — an underscore after sk, not the hyphen the regex requires. GitLab's personal, project, and group access tokens default to a glpat- prefix. And as of npm's November 2025 security update, classic (unprefixed) tokens were retired — every current npm access token now carries the npm_ prefix, so this isn't a partial gap for npm, it's total. None of the three share the exact hyphen-delimited shape the existing four regexes were written for, so all three return false — the same value looksLikeHardcodedSecret returns for an actual placeholder.

The general backstop has the same four providers

secrets-scan.js greps every git-tracked file — so even though .mcp.json only gets the specific check above, the general scan runs against it too, in theory as a second line of defense. Its SECRET_PATTERNS list is a separate implementation of the same four providers:

const SECRET_PATTERNS = [
  { name: 'AWS Access Key ID', regex: /AKIA[0-9A-Z]{16}/g },
  { name: 'GitHub Personal Access Token', regex: /ghp_[a-zA-Z0-9]{36}/g },
  { name: 'Anthropic/OpenAI-style secret key', regex: /sk-[a-zA-Z0-9]{20,}/g },
  { name: 'Slack token', regex: /xox[baprs]-[a-zA-Z0-9-]{10,}/g },
  { name: 'Private key block', regex: /-----BEGIN (RSA |EC |OPENSSH )?PRIVATE KEY-----/g },
];

Same gap, same three providers missing. A Stripe, GitLab, or npm token doesn't match any named pattern here either.

The generic fallback: built for key: "value", not JSON

Anticipating exactly this kind of gap, secrets-scan.js also has a catch-all that doesn't care about the provider — it flags any quoted 20+ character value assigned to a key that looks like a credential:

const GENERIC_SECRET_PATTERN =
  /(?:api[_-]?key|secret|password|token)\s*[:=]\s*['"]([^\s'"]{20,})['"]/gi;

This is the pattern that should backstop the Stripe key regardless of format, since it doesn't check the value's shape at all — only the key name next to it. Run against the exact syntax .mcp.json uses:

'"secret": "sk_live_51H8xJ2KZvczFKz_EXAMPLE_NOT_REAL_0000"'
  → NO MATCH

'secret: "sk_live_51H8xJ2KZvczFKz_EXAMPLE_NOT_REAL_0000"'
  → matches, captures sk_live_51H8xJ2KZvczFKz_EXAMPLE_NOT_REAL_0000

Only the quote changes between the two lines. The pattern requires secret (or token/password/ api_key) to be followed by \s*[:=] — whitespace, then a colon or equals sign. In YAML or a shell-style .env line, the key sits bare before the colon or equals, so that holds. In JSON, the key is itself inside quotes: "secret": has a " character between the word and the colon, which \s* doesn't absorb. The pattern that exists specifically to catch what the named-provider patterns miss doesn't match JSON's own key syntax — the exact syntax .mcp.json, package.json, and most config files in a Claude Code project are written in.

The realistic key name compounds the problem independently of the quote: an env var is more often named STRIPE_SECRET_KEY than bare secret, and \s*[:=] requires the matched keyword to be immediately followed by the delimiter with only whitespace in between. "STRIPE_SECRET_KEY": "sk_live_..." has _KEY" sitting between SECRET and the colon, so it fails this pattern for that reason too, independent of the JSON-quote issue above.

Put together

A real .mcp.json entry —

{
  "mcpServers": {
    "billing": {
      "command": "node",
      "args": ["billing-mcp.js"],
      "env": { "STRIPE_SECRET_KEY": "sk_live_51H8xJ2KZvczFKz_EXAMPLE_NOT_REAL_0000" }
    }
  }
}

— produces no finding from any of the three mechanisms above: not looksLikeHardcodedSecret (wrong prefix shape), not SECRET_PATTERNS (same four providers), not GENERIC_SECRET_PATTERN (JSON quote breaks the delimiter match, and the compound key name would break it separately even in YAML). This was verified by running each function directly against the literal string above and its constituent parts, not by reading the regex and assuming — all three "no match" results were reproduced in a Node REPL.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README. None of the fixtures in that corpus use a Stripe, GitLab, or npm token shape, so this gap doesn't move either number; it's a coverage hole the existing corpus was never built to catch, not a regression. Nothing in this article changes cc-doctor's code — it documents the exact conditions under which the three checks above stay silent, with the reproduction steps to verify it independently.
