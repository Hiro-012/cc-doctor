cc-doctor flags Bash(curl ... | sh) in settings.json — not | bash), the far more common install-script idiom

By HiroCheck · Published 2026-09-22

Among the six fixed patterns lib/checks/settings-permissions.js checks every Bash allow-rule against (covered in an earlier post on this blog), one is meant to catch the classic "download a script and run it as root" idiom:

/^Bash\(curl.*\|\s*sh\)/

Read literally, this matches an allow rule that ends in a pipe to sh), with any amount of whitespace after the pipe. It does not match a pipe to anything else. And the interpreter named in that regex, plain sh, is the less common half of this idiom in practice — most published install one-liners (nvm, rustup, Homebrew's own installer historically, countless others) say | bash, not | sh, specifically because they rely on Bash-only syntax the POSIX sh the pattern checks for isn't guaranteed to support.

Verified directly, side by side

Two otherwise-identical .claude/settings.json files, differing only in the interpreter named after the pipe, scanned by the unmodified CLI:

// piped-sh/.claude/settings.json
{ "permissions": {
    "allow": ["Bash(curl https://example.com/install.sh | sh)"],
    "deny": ["Bash(rm -rf /)"] } }

// piped-bash/.claude/settings.json
{ "permissions": {
    "allow": ["Bash(curl https://example.com/install.sh | bash)"],
    "deny": ["Bash(rm -rf /)"] } }
$ cc-doctor piped-sh
[ERROR] settings-permissions: .claude/settings.json allows a high-risk
  command pattern: "Bash(curl https://example.com/install.sh | sh)"
cc-doctor: 1 error(s), 0 warning(s), 1 info.
$ echo $?
1

$ cc-doctor piped-bash
cc-doctor: 0 error(s), 0 warning(s), 1 info.
$ echo $?
0

A third variant piping to zsh instead produces the same clean exit as bash. All three grant Claude Code the identical thing — permission to fetch and immediately execute a remote script, unreviewed, without a prompt — and cc-doctor's own README lists this exact pattern ("curl-pipe-to-shell install scripts") as one of the six shapes it claims to catch. It catches one of the (at least) three interpreter names that idiom is actually written with.

Why the regex, not just the interpreter list, is the actual gap

The fix isn't "add bash and zsh as two more literals" — that just narrows the miss to the next interpreter someone writes (dash, ksh, a full path like /bin/bash). The pattern is checking for a specific word immediately before the closing parenthesis when what it actually wants to know is "does this rule pipe a curl response into some shell interpreter at all" — which is answerable without naming any interpreter, e.g. matching a pipe into any single bare word (no flags, no further pipeline) preceding the closing paren. As written, the regex is interpreter-enumerable, and the one interpreter it enumerates is not the one most real install scripts use.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: risky Bash allow-rules, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's accuracy corpus, the tool's recall is 100.0% (29/29) with a 0.0% false-positive rate (0/20) — full methodology in the project README. That corpus doesn't include a curl | bash-style fixture, so this gap doesn't change those numbers; it's a real miss the existing corpus simply doesn't exercise.
