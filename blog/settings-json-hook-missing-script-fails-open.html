A Claude Code hook with a mistyped script path doesn't block anything — it fails open, silently

By HiroCheck · Published 2026-09-04

A team adds a PreToolUse hook to .claude/settings.json to block dangerous Bash commands before Claude Code runs them — a guard script under .claude/hooks/. The script gets renamed during a refactor, or the hooks/ directory is accidentally left out of a commit, or the path is just typed wrong. The settings.json entry still parses as valid JSON and Claude Code never complains at startup. Every future session runs as if the hook were never configured at all, and nothing in the normal transcript says so.

What Claude Code's own docs say happens

Per Claude Code's hooks documentation, when a hook command can't even start — because the script path doesn't exist or isn't executable — the shell exits with a code like 127, and for most hook events the action proceeds anyway. That's "fail open" by design, not a bug: exit code 2 is the only code that blocks an action through the code alone, and a hook that never runs can't produce exit code 2. The interpreter's error (/bin/sh: /path/to/hook.sh: No such file or directory) is reported as a non-blocking notice, and stderr from a hook run this way is written to the debug log only — never the transcript, and Claude never sees it. The documentation names this exact failure mode directly: "a mistyped path in settings.json leaves the gate silently disabled."

In other words, a broken hook path isn't a loud failure a reviewer would notice — it's a silent no-op. The permission gate a team believes is enforcing policy is, in this state, enforcing nothing.

Reproducing it

A minimal repo with a PreToolUse hook pointing at a script that was never committed:

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/block-dangerous-bash.sh" }
        ]
      }
    ]
  }
}

.claude/hooks/ doesn't exist in this repo at all — only .claude/settings.json is tracked. Running checkSettingsPermissions() (cc-doctor's lib/checks/settings-permissions.js) against it:

[WARN] [warn] settings-permissions: .claude/settings.json hook for
"PreToolUse" references a script that does not exist:
.claude/hooks/block-dangerous-bash.sh (.claude/settings.json)

The check walks every hook event in settings.json and settings.local.json, extracts the leading script path from each command-type hook's command string (matching a .sh/.js/.py/.mjs/.cjs suffix), resolves it relative to the repo root, and confirms the file is actually there with existsSync. It doesn't try to determine whether the script is executable, whether it exits 0 or 2, or whether the matcher would ever fire for a given tool call — only whether the path Claude Code would try to run exists on disk at all. That's a narrower question than "does this hook work," but it's exactly the failure mode the documentation calls out by name: a path that's wrong.

Why this check is easy to miss the value of

Every other cc-doctor check in settings-permissions.js looks for something present that shouldn't be — an unscoped Bash(*) grant, a dangerous allow-rule pattern, a committed settings.local.json. This is the one check in the file that looks for something absent that a team believes is present: a script the settings file claims exists, guarding a tool call, that in fact does nothing. A missing guard script produces no error at commit time, no error at Claude Code startup, and — per the documentation above — no error in the normal transcript either. The gap between "the policy is configured" and "the policy is enforced" is invisible unless something specifically checks the referenced path against the filesystem.
