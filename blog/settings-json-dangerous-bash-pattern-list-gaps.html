cc-doctor flags Bash(git push --force) in settings.json — not Bash(git push -f) or Bash(git reset --hard)

By HiroCheck · Published 2026-08-30

Claude Code's own permission engine is careful about what an allow rule actually authorizes at runtime: per its documentation, it's aware of shell operators, splitting a command on &&, ||, ;, |, |&, &, and newlines, and requiring each resulting subcommand to match a rule independently — a rule like Bash(safe-cmd *) doesn't authorize safe-cmd && other-cmd. It also strips known wrapper commands (timeout, time, nice, nohup, stdbuf) and safe environment-variable prefixes before matching, so a rule written for the inner command still applies once those are peeled away. That's a real command parser doing real work.

cc-doctor's settings-permissions check is a much smaller thing, and doesn't try to be that parser. It reads a committed .claude/settings.json or settings.local.json, takes each string in permissions.allow, and tests it against six fixed regular expressions. If none match, the rule passes silently — regardless of what the rule would actually let Claude Code run.

The six patterns

From lib/checks/settings-permissions.js, verbatim:

/^Bash\(\*\)$/
/^Bash\(rm\s+-rf/
/^Bash\(git\s+push\s+--force/
/^Bash\(sudo(\s|\))/
/^Bash\(curl.*\|\s*sh\)/
/^Bash\(.*--dangerously-skip-permissions/

Plus a separate check that flags Bash(*) specifically when the same file has zero deny rules. That's the entire list cc-doctor's README describes as "other high-risk allowlisted command patterns" — six shapes, matched as plain substrings against the rule's own text.

Three rules that don't match, verified directly

Rather than argue about the six-pattern list in the abstract, we ran checkSettingsPermissions() against a .claude/settings.json whose permissions.allow contained five rules — three constructed as near-misses, plus a working positive control and a working negative control to confirm the check was actually running:

"Bash(git push -f origin main)",
"Bash(git push --force-with-lease origin main)",   // control: matches
"Bash(git reset --hard origin/main)",
"Bash(chmod -R 777 /)",
"Bash(rm -rf /)"                                   // control: matches

Output — only the two controls produced a finding:

[
  ".claude/settings.json allows a high-risk command pattern: \"Bash(git push --force-with-lease origin main)\"",
  ".claude/settings.json allows a high-risk command pattern: \"Bash(rm -rf /)\""
]

The other three passed with no warning at all:

  • git push -f — the short flag for --force, same operation, same risk (overwriting remote history other people may have already pulled). The regex requires the literal substring --force immediately after push, so the one-letter alias it's short for isn't recognized. (--force-with-lease, by contrast, does match — it happens to start with the same eight characters the regex looks for, which is what makes the -f gap visible: two rules naming the same underlying git flag, one flagged and one not, purely because of how each one spells it.)
  • git reset --hard — discards uncommitted changes and moves the branch pointer, unrecoverable the same way rm -rf or a force-push is. There's no pattern for it; the list's only git-specific entry is the force-push one.
  • chmod -R 777 — recursively makes a directory tree world-writable. Not represented by any of the six shapes.

Why this isn't really about finding more patterns to add

Each of these three could be patched into the list with one more regex — and probably should be, they're common enough. But the shape of the problem doesn't go away: a fixed list of literal command shapes is enumerating an open set. git branch -D, docker system prune -af, find / -delete, and any destructive command a project's own tooling happens to wrap in a differently-named script are all outside the six patterns today, and adding today's three doesn't close that gap for tomorrow's fourth. That's a different failure mode from cc-doctor's other checks — the secrets-scan check's five-pattern set is also finite, but it's matched against file content the scanner doesn't control; here the six patterns are trying to enumerate every dangerous allow rule someone might write, a much larger and less bounded space. Nothing in this check inspects what a rule would actually let Claude Code execute, the way Claude Code's own runtime matcher does — it's purely a lexical check for whether a handful of known-bad shapes appear in the rule text.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README. That corpus targets the secrets-scan check; the settings-permissions gap described here doesn't change those numbers, since none of the three rules above triggered a false negative against an existing fixture — they simply aren't part of the corpus.
