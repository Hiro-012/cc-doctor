Notes on the Claude Code config and secret-exposure issues cc-doctor catches, and why they matter.

Two Claude Code config mistakes that leak secrets or grant too much

Why a hardcoded Authorization header in .mcp.json and an unrestricted Bash(*) permission in .claude/settings.json are both common, both easy to make by accident, and both checkable in one CLI run.

settings.local.json is supposed to stay local — what happens when it gets committed

Claude Code's own convention keeps .claude/settings.local.json out of git for a reason: it holds one contributor's personal permission grants and local paths. Here's what leaks when that convention breaks, and a second check for hooks pointing at scripts that no longer exist.

Deleting the line doesn't rotate the key — what "remove it from git history" actually means

cc-doctor's secrets-scan check reads git-tracked files as they exist right now, not the commits that came before. Here's the gap that leaves open, why cc-doctor's own warning tells you to do two separate things, and what actually gets a secret out of history.

CLAUDE.md gets read into every session — cc-doctor's check on it only catches 3 shapes of secret

CLAUDE.md is merged into every Claude Code session automatically, including a global copy outside any repo. cc-doctor's claude-md check only flags PGP blocks, private-key headers, and AWS access key IDs in the project-root file — here's what that leaves uncovered, and why it mostly doesn't matter for the tracked-file case.

cc-doctor flags Bash(git push --force) in settings.json — not Bash(git push -f) or Bash(git reset --hard)

cc-doctor's settings-permissions check flags six specific shapes of risky Bash allow-rule in .claude/settings.json. git push -f (the short flag for --force), git reset --hard, and chmod -R 777 are just as destructive but aren't among the six — verified by running the check against each rule directly.

A Claude Code hook with a mistyped script path doesn't block anything — it fails open, silently

Claude Code's own docs say a hook command that can't start (missing or non-executable script) fails open: the tool call proceeds, and the error goes to the debug log only, never the transcript. cc-doctor's settings-permissions check catches this by testing the referenced path exists — verified by reproducing the exact failure and running the check against it.

cc-doctor has two checks for Bash(*) in settings.json — one of them can never fire on its own

settings-permissions.js flags an unscoped Bash(*) allow rule twice: once unconditionally, once only when deny is empty. The second condition is a strict subset of the first, so it can never produce a finding the first one hasn't already produced for the same rule — verified by tracing both conditions and reproducing all three deny-list states.

A Stripe live key hardcoded in .mcp.json slips past every one of cc-doctor's secret checks

mcp-config.js's hardcoded-secret regex only recognizes four providers' key formats (OpenAI/Anthropic, GitHub, AWS, Slack). Stripe (sk_live_/rk_live_), GitLab (glpat-) and npm (npm_) tokens don't match any of them — and secrets-scan.js's generic fallback pattern, meant to backstop exactly this gap, doesn't match standard JSON key syntax either. Verified by running both checks against real-shaped (fake) values.

A committed .env file with a plainly-named password in it produces zero findings from cc-doctor

secrets-scan.js's generic fallback pattern requires the assigned value to be wrapped in quotes. Standard .env syntax (KEY=value, no quotes) is the one place that requirement can never be met, so any secret whose format isn't already one of the five named patterns evades detection entirely, however the key is named. Verified by committing a two-line .env file and running the real CLI against it.

cc-doctor's hook-script check: silent on "python3 foo.py", false alarm on Claude Code's own $CLAUDE_PROJECT_DIR convention

settings-permissions.js only looks for a missing hook script when the command's first token itself ends in .sh/.js/.py/.mjs/.cjs. An interpreter-prefixed command like `python3 hooks/foo.py` — the exact form of Anthropic's own example hook — never gets checked at all, so a genuinely missing script produces zero warning. The opposite case is also wrong: $CLAUDE_PROJECT_DIR, the path prefix Claude Code's own docs recommend for hook commands, makes the check report a script as missing even when it exists, because the literal variable string is never expanded before the existsSync() call. Both reproduced against the real CLI.

cc-doctor's .mcp.json secret check never looks at "args" — the exact field Context7's own docs tell you to put your API key in

mcp-config.js's hardcoded-secret scan reads server.env and server.headers. It never reads server.args — the field Upstash's own Context7 MCP quickstart tells users to pass --api-key in. A GitHub-token-shaped secret placed there is caught only by the unrelated whole-file backstop; a real Context7 key format is caught by nothing at all. Verified by running the unmodified CLI against both placements.

cc-doctor flags "Bash(*)" in settings.json — not bare "Bash", which Claude Code's own docs say grants the same unrestricted access

cc-doctor's settings-permissions check looks for the literal string Bash(*) in permissions.allow. Claude Code's own permissions documentation describes a bare Bash entry (no parentheses) as an equivalent unscoped grant — recommended, even, as the way to allow all Bash commands without prompts. cc-doctor produces zero findings against it. Verified against the unmodified CLI.

cc-doctor flags "Bash(curl ... | sh)" in settings.json — not "| bash)", the far more common install-script idiom

cc-doctor's dangerous-Bash-pattern regex for curl-pipe-to-shell is anchored to the literal interpreter name \"sh\": /^Bash(curl.*\|\s*sh\)/. \"Bash(curl ... | bash)\" and \"Bash(curl ... | zsh)\" — the actual install-script one-liners most projects publish — don't match. Verified side by side against the unmodified CLI.

cc-doctor's secret scan silently skips any tracked file over 1MB — no pattern check runs on it at all

secrets-scan.js's MAX_FILE_BYTES guard discards a file before any of the five named patterns or the generic fallback ever run against it. A committed bundle, minified asset, or data dump just over 1MB with a literal secret produces zero findings; the identical content trimmed under the limit is correctly flagged. Verified against the unmodified CLI.

cc-doctor's dangerous-Bash-pattern list only looks at the first command in an allow rule — chain anything in front and it goes quiet

Four of the six regexes in settings-permissions.js's DANGEROUS_BASH_PATTERNS array (rm -rf, git push --force, sudo, curl ... | sh) are anchored to the start of the Bash(...) string. Bash(sudo rm -rf /) is flagged; Bash(cd /tmp && sudo rm -rf /) and Bash(echo ok; curl ... | sh) are not — same destructive command, one extra shell operator in front. Verified against the unmodified CLI.

cc-doctor's GitHub-token detection only knows the old ghp_ format — GitHub's own recommended fine-grained PATs are invisible

Both of cc-doctor's GitHub-token checks (mcp-config.js's hardcoded-secret scan and secrets-scan.js's named pattern) match only the legacy ghp_ classic PAT. A github_pat_-prefixed fine-grained token — the format GitHub's own UI has recommended by default for years — hardcoded in .mcp.json's env block produces zero output, while the identical classic-format token is caught immediately. Verified against the unmodified CLI.

cc-doctor's dangerous-Bash-pattern check never runs on hook commands — only on permissions.allow rules

DANGEROUS_BASH_PATTERNS (rm -rf, git push --force, sudo, curl | sh, --dangerously-skip-permissions) is applied to every string in permissions.allow, but settings-permissions.js's hook loop never calls it at all — a hook's command is only ever checked for whether a referenced script file exists. A PreToolUse hook whose command is literally rm -rf / produces zero findings; the identical string as an allow rule is flagged immediately. Verified against the unmodified CLI.
