cc-doctor's GitHub-token detection only knows the old ghp_ format — GitHub's own recommended fine-grained PATs are invisible

By HiroCheck · Published 2026-09-28

cc-doctor has two places that specifically look for a GitHub token: the .mcp.json hardcoded-secret check, and a named pattern in the general secrets scan. Both recognize only GitHub's legacy "classic" personal access token format (ghp_...). GitHub's fine-grained personal access tokens — prefixed github_pat_ instead, and the format GitHub's own token-creation UI has defaulted to recommending since 2022 — match neither check, in any form.

Where the ghp_-only assumption lives

lib/checks/mcp-config.js's looksLikeHardcodedSecret():

/^ghp_[a-zA-Z0-9]{20,}$/.test(value) || // GitHub PAT

lib/checks/secrets-scan.js's named pattern list:

{ name: 'GitHub Personal Access Token', regex: /ghp_[a-zA-Z0-9]{36}/g },

Neither regex has any branch for the github_pat_ prefix. A fine-grained token simply never matches either expression, regardless of length or content after the prefix.

Case 1: the exact scenario mcp-config.js exists for

Two otherwise-identical, git-tracked .mcp.json fixtures, differing only in the token format in env.GITHUB_TOKEN:

// fine-grained/.mcp.json
{ "mcpServers": { "github": {
    "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": { "GITHUB_TOKEN": "github_pat_11AAAAAAA0FAKEexample...gklmnop" }
}}}

// classic/.mcp.json — same shape, only the token format changed
{ "mcpServers": { "github": {
    "command": "npx", "args": ["-y", "@modelcontextprotocol/server-github"],
    "env": { "GITHUB_TOKEN": "ghp_AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA" }
}}}

Running the unmodified CLI against each:

=== fine-grained (github_pat_) ===
[INFO] [info] claude-md: No CLAUDE.md found. Optional, but it lets Claude Code pick up
  project-specific conventions automatically. (CLAUDE.md)
cc-doctor: 0 error(s), 0 warning(s), 1 info.
EXIT: 0

=== classic (ghp_) control ===
[ERROR] [error] mcp-config: .mcp.json server "github" has what looks like a hardcoded secret
  in env.GITHUB_TOKEN. Use an env var reference (e.g. "${GITHUB_TOKEN}") instead of committing
  the literal value. (.mcp.json)
[ERROR] [error] secrets-scan: Possible GitHub Personal Access Token committed in .mcp.json.
  If real, rotate it immediately and remove it from git history. (.mcp.json)
cc-doctor: 2 error(s), 0 warning(s), 1 info.
EXIT: 1

Same file structure, same key, same server entry — moving from ghp_ to github_pat_ takes the finding count from two to zero. This is precisely the case mcp-config.js was written to catch: a hardcoded credential in an MCP server's env block. It misses it completely when the credential is in the format GitHub itself steers users toward.

Case 2: outside .mcp.json, only the generic fallback catches it, mislabeled

The same fine-grained token pasted into a plain Python file as a key = "value" assignment:

// config.py
GITHUB_TOKEN = "github_pat_11AAAAAAA0FAKEexample...gklmnop"
$ node bin/cli.js .
[ERROR] [error] secrets-scan: Possible Generic assigned secret committed in config.py.
  If real, rotate it immediately and remove it from git history. (config.py)
cc-doctor: 1 error(s), 0 warning(s), 1 info.
EXIT: 1

This one is caught — but only by GENERIC_SECRET_PATTERN, the catch-all that matches on the surrounding token\s*[:=]\s*"..." syntax, not on the token looking like a GitHub credential. The finding is reported as a generic "Generic assigned secret," not identified as a GitHub token, and that same generic fallback is defeated inside JSON files by the quote-before-colon shape a CLI-flag or array-element placement produces — a limitation this blog has documented before for a different value shape. Inside .mcp.json's env block specifically (Case 1), the generic fallback would apply too in principle, but it never gets the chance: cc-doctor doesn't need it there, because that's exactly the field mcp-config.js's dedicated check is supposed to cover — and doesn't, for this format.

Not a hypothetical format

GitHub has recommended fine-grained personal access tokens as the default choice in its token-creation UI (Settings → Developer settings → Personal access tokens) since introducing them in 2022, specifically because they support repository-scoped and time-limited permissions that classic tokens don't. A team that hardcodes a credential today — by mistake, in an .mcp.json committed while wiring up an MCP server — is now more likely to be holding a github_pat_ token than a ghp_ one.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's accuracy corpus (node --test test/accuracy.test.js, run unmodified for this article):

#   detected (true positives): 29

Full methodology in the project README. No fixture in test/accuracy.test.js or test/scan.test.js uses a github_pat_-format token, so this gap moves neither number — it's a coverage hole, not a regression. Nothing in this article changes cc-doctor's code; both reproductions above ran against the unmodified CLI (npm test: 60/60 passing).
