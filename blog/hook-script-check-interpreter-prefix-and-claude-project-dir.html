cc-doctor's hook-script check: silent on python3 foo.py, false alarm on Claude Code's own $CLAUDE_PROJECT_DIR convention

By HiroCheck · Published 2026-09-15

cc-doctor's settings-permissions.js warns when a hooks entry in .claude/settings.json points at a script that doesn't exist on disk. It does this by pattern-matching the first token of the hook's command string, then calling existsSync() on whatever it extracts. Both steps assume the command is the script path — an assumption that breaks in two opposite directions once you look at how hook commands are actually written, including in Anthropic's own example and its own documented best practice.

The check

if (hook.type === 'command' && typeof hook.command === 'string') {
  const scriptPathMatch = hook.command.match(/^([^\s]+\.(sh|js|py|mjs|cjs))/);
  if (scriptPathMatch) {
    const scriptPath = scriptPathMatch[1];
    const resolved = scriptPath.startsWith('/')
      ? scriptPath
      : join(root, scriptPath);
    if (!existsSync(resolved)) {
      report.warn(/* ... references a script that does not exist ... */);
    }
  }
}

Two things have to hold for this to work: the command's first whitespace-delimited token has to end in one of five extensions, and whatever precedes the script path in join(root, scriptPath) has to resolve to nothing so the literal string is a valid relative path. Neither holds for two hook-writing styles that are common enough to appear in Claude Code's own materials.

Case 1: an interpreter prefix means no check ever runs

Anthropic's own example hook in the claude-code repository is invoked as "command": "python3 /path/to/.../bash_command_validator_example.py" — the interpreter named first, the script as an argument. Feed cc-doctor that shape with the script actually missing:

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [
        { "type": "command", "command": "python3 hooks/block_dangerous_bash.py" }
      ]}
    ]
  }
}

hooks/block_dangerous_bash.py does not exist anywhere in this repo. Running checkSettingsPermissions() against it:

cc-doctor: 0 error(s), 0 warning(s), 1 info.

Nothing. The regex tests the string "python3 hooks/block_dangerous_bash.py" against /^([^\s]+\.(sh|js|py|mjs|cjs))/: the first token is python3, which has no matching extension, so the whole match fails before scriptPath is ever extracted. The same settings file with the command changed to a direct invocation — ".claude/hooks/block.sh", script equally missing — does get flagged:

[WARN] [warn] settings-permissions: .claude/settings.json hook for
"PreToolUse" references a script that does not exist:
.claude/hooks/block.sh (.claude/settings.json)

Same underlying condition — a hook command names a script that isn't there — two different outcomes purely because of how the command happens to be written. Any hook script run through python3, node, bash, or any other interpreter named first is invisible to this check, whether the script is present or not.

Case 2: Claude Code's own recommended prefix triggers a false alarm

Claude Code's hooks documentation recommends prefixing hook script paths with $CLAUDE_PROJECT_DIR specifically to avoid a different, real bug: hooks resolve relative paths against the process's current working directory, not the project root, so a plain relative path can break the moment a session's working directory isn't the project root. The documented fix is exactly this shape:

"command": "$CLAUDE_PROJECT_DIR/.claude/hooks/check-style.sh"

Using the ${...} form (also valid, and the one shown in Claude Code's own settings examples) with a script that does exist on disk:

.claude/hooks/present.py   # exists, tracked in git

{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash", "hooks": [
        { "type": "command", "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/present.py" }
      ]}
    ]
  }
}
[WARN] [warn] settings-permissions: .claude/settings.json hook for
"PreToolUse" references a script that does not exist:
${CLAUDE_PROJECT_DIR}/.claude/hooks/present.py (.claude/settings.json)

The script is right there in .claude/hooks/present.py, and cc-doctor reports it missing. This time the regex matches fine — the whole string ends in .py — but scriptPath.startsWith('/') is false (the string starts with $, not /), so it falls into join(root, scriptPath), producing a path like <root>/${CLAUDE_PROJECT_DIR}/.claude/hooks/present.py. ${CLAUDE_PROJECT_DIR} is never a real directory name on disk — it's a shell/Claude Code environment-variable reference meant to be expanded before the command runs — so existsSync() on that joined path is false by construction, for every hook written the way Claude Code's own docs tell you to write it.

Same root cause, opposite symptoms

Both cases come from treating hook.command as if it were always literally a filesystem path, with no notion of an interpreter prefix or of shell/environment-variable expansion. One direction makes the check silent when it should warn (interpreter-prefixed commands, a missing script produces nothing). The other makes it warn when it shouldn't ($CLAUDE_PROJECT_DIR-prefixed commands, a present script gets flagged as absent). A team that follows Claude Code's own best-practice advice and prefixes its hook paths with $CLAUDE_PROJECT_DIR will see a permanent, unfixable-by-them warning from cc-doctor on every scan — which is the kind of noise that tends to end with the warning being ignored altogether, including the next time it's right.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README. The corpus's only hook-related fixtures use a direct .sh path, one missing and one present; neither an interpreter-prefixed command nor a $CLAUDE_PROJECT_DIR-prefixed command appears in either fixture set, so this gap moves neither number — it's a blind spot the corpus was never built to catch, not a regression. Nothing in this article changes cc-doctor's code; both reproductions above were run against the unmodified CLI.
