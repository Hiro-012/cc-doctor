cc-doctor has two checks for Bash(*) in settings.json — one of them can never fire on its own

By HiroCheck · Published 2026-09-06

lib/checks/settings-permissions.js contains two separate pieces of logic that both react to an unscoped Bash(*) allow rule in .claude/settings.json. Tracing their conditions shows one is a strict subset of the other: every input that trips the narrower check has already tripped the broader one, so the narrower check has no state in which it can report something the broader one hasn't already reported for the same rule.

The two conditions, side by side

const DANGEROUS_BASH_PATTERNS = [
  /^Bash\(\*\)$/,               // ← check A, one of six patterns
  /^Bash\(rm\s+-rf/,
  /^Bash\(git\s+push\s+--force/,
  /^Bash\(sudo(\s|\))/,
  /^Bash\(curl.*\|\s*sh\)/,
  /^Bash\(.*--dangerously-skip-permissions/,
];

for (const rule of allow) {
  for (const pattern of DANGEROUS_BASH_PATTERNS) {
    if (pattern.test(rule)) report.error(...);      // fires on rule alone
  }
}

if (allow.includes('Bash(*)') && deny.length === 0) {  // ← check B
  report.error(...);                                    // fires on rule + empty deny
}

Check A fires the instant 'Bash(*)' appears anywhere in allow — it doesn't look at deny at all. Check B fires only when that same exact string is present and deny is empty. Both conditions require the identical substring test on the identical array element; check B just adds one more requirement on top. That means check B's trigger condition is never true unless check A's trigger condition is also true, for the same rule, in the same run.

Reproducing all three states

Running checkSettingsPermissions() against three otherwise-identical .claude/settings.json files that vary only the deny array:

// deny: [] (empty)
{ "permissions": { "allow": ["Bash(*)"], "deny": [] } }
→ [
    "allows a high-risk command pattern: \"Bash(*)\"",           // check A
    "grants unrestricted Bash access (\"Bash(*)\") with no deny rules."  // check B
  ]

// deny: ["Bash(rm -rf /)"]  (one narrow, unrelated rule)
{ "permissions": { "allow": ["Bash(*)"], "deny": ["Bash(rm -rf /)"] } }
→ [ "allows a high-risk command pattern: \"Bash(*)\"" ]          // check A only

// no Bash(*) at all
{ "permissions": { "allow": ["Bash(git commit *)"], "deny": [] } }
→ []                                                              // neither

The middle case is the one that matters: adding a single deny rule — any deny rule, whether or not it has anything to do with what Bash(*) actually exposes — silences check B's message entirely. It does not silence check A's, and check A's message ("allows a high-risk command pattern") already says everything check B's more specific wording ("no deny rules") would have added. A repo with Bash(*) and one irrelevant deny rule reports exactly one error either way it's configured, worded identically to the zero-deny case. Nothing is lost; check B's own condition on deny just never gets the chance to be the reason something was flagged.

Why the accuracy corpus never caught this

cc-doctor's own test corpus has a fixture built specifically to confirm a rule survives a deny list: P-settings-bash-star-with-deny (allow: ['Bash(*)'], deny: ['Bash(rm -rf /)']), asserting the case is still flagged. It is — via check A. But the assertion is has(f, x => x.check === 'settings-permissions' && x.severity === 'error'): any error from the check module counts as a pass, not a specific message. Since check A alone already satisfies that assertion, the fixture can't distinguish "check B contributed a finding" from "check B did nothing and check A carried the whole result," which is exactly what happens. Recall on this fixture has always been, and will always be, 100% regardless of whether check B's code exists at all — the corpus measures whether a finding came back, not which line produced it.

Why "just add a deny rule" wasn't the fix anyway

Claude Code's own permissions documentation is explicit that rules are evaluated in a fixed order — deny, then ask, then allow — and that "a deny rule can't carry allowlist exceptions": a broad allow like Bash(*) stays in effect for every command except the ones a deny rule specifically names. One narrow deny entry doesn't shrink what Bash(*) permits elsewhere by even one command; it only carves out the exact thing it names. The documentation separately warns that Bash rules trying to constrain arguments are "fragile" — its own example is a curl http://github.com/* rule that a differently-ordered flag, a redirect, or a variable substitution slips past — so even a deny rule aimed at a real risk isn't a guarantee the way its author might assume. Check B's silence condition (deny is non-empty) was never actually verifying that the added protection meant anything; it was only checking that the array wasn't literally empty.

What cc-doctor checks

cc-doctor is a free CLI that scans a repo's git-tracked files for hardcoded secrets, plus Claude Code-specific misconfigurations: an unscoped Bash(*) permission grant, a committed settings.local.json, hooks pointing at scripts that no longer exist, and hardcoded credentials in .mcp.json. It runs entirely against the local filesystem and git index — no network access, no API key required.

npx cc-doctor            # scan the current directory
npx cc-doctor path/to/repo

Measured against cc-doctor's 49-fixture accuracy corpus, the tool's recall is 100% (29/29 known-bad fixtures) with a 0% false-positive rate (0/20 known-clean fixtures) — full methodology in the project README. Nothing above changes those numbers: every fixture that exercises check B also exercises check A on the same rule, so removing check B entirely — which this session has not done, only measured — would not lower recall on the existing corpus by a single fixture.
